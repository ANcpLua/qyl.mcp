Every must-know on the owner's list is confirmed, with two precisions: the proto UTF-8 rules are SHOULDs, and "CPU usage in cores" changes only the description, not the instrument or the unit. Because qyl vendors OTLP at v1.8.0, the proto section also covers 1.9.0 to 1.11.0, and 1.11.0 adds a MUST that qyl breaks today (OTLP-2).

Rules applied: no qyl attribute is renamed as incidental cleanup; the Collector supports new vocabulary before a producer emits it; the Codex agent owns the TypeScript convention generator and the qyl.mcp import migration.

## opentelemetry-proto 1.11.1, measured from QYL's v1.8.0 pin

| ID | Upstream change | Where it lands | Decision |
|---|---|---|---|
| OTLP-1 | UTF-8 (1.11.1, [#845](https://github.com/open-telemetry/opentelemetry-proto/pull/845), "UTF-8 String Handling" in `docs/specification.md`): encoders SHOULD write valid UTF-8 into `string` fields; decoders SHOULD replace invalid sequences with U+FFFD; intermediaries MAY pass strings through unchecked | The encoders comply. OTel JS 0.223.0 writes non-ASCII strings with `TextEncoder` (MCP), and OTel .NET 1.19.1 writes them with `Encoding.UTF8` (AI, the QYL tools); both turn a lone surrogate into U+FFFD. The Collector does not replace. Google.Protobuf 3.36.1 decodes `string` fields with `UTF8Encoding(throwOnInvalidBytes: true)` and throws `InvalidProtocolBufferException.InvalidUtf8` (protobuf v36.1 `csharp/src/Google.Protobuf/ParsingPrimitives.cs:29-30,585-589`), so one bad string rejects the whole export. OTLP/HTTP protobuf (`services/qyl.collector.ingestion/OtlpPayloadParser.cs:63`) answers 400 (`services/qyl.collector/Hosting/CollectorEndpointExtensions.cs:104,189,274`). gRPC fails in the generated marshallers before the services run (`CollectorEndpointExtensions.cs:37-39`). OTLP/JSON fails where `Utf8JsonReader.GetString` meets invalid UTF-8 or an unpaired surrogate escape (`OtlpJsonIdNormalizer.cs:48,58,60`); AT can forward such an escape from a crafted `route` (`worker/index.ts:102`). | **Adopt now** in QYL: decode with U+FFFD on all three paths. Google.Protobuf has no lenient mode, so after a strict parse fails with `InvalidUtf8`, repair the `string` fields and parse again. Valid payloads keep the current path. |
| OTLP-2 | Request size limits (1.11.0, [#782](https://github.com/open-telemetry/opentelemetry-proto/pull/782)): the server MUST bound the request, including after decompression. Over the limit, OTLP/HTTP MUST answer `413 Content Too Large` and gRPC MUST answer `RESOURCE_EXHAUSTED`. 64 MiB is RECOMMENDED and SHOULD be configurable. | Neither path complies. OTLP/HTTP bounds the decompressed body at 16 MiB (`OtlpPayloadParser.cs:12,86-87,127-128`) but answers with 400 (`CollectorEndpointExtensions.cs:104,189,274`). gRPC answers `ResourceExhausted`, but Grpc.AspNetCore 2.84.0 (`Version.props:80`) applies its 4 MB default to the compressed message only and then decompresses gzip and deflate without a cap (grpc-dotnet v2.84.0 `src/Grpc.AspNetCore.Server/Internal/PipeExtensions.cs:382,442-458`). QYL sets neither a limit nor its own compression providers (`services/qyl.collector/Hosting/CollectorCoreExtensions.cs:23-29`). | **Adopt now** in QYL: answer an oversized OTLP/HTTP body with 413, and cap the decompressed gRPC message with compression providers that stop at the limit and answer `ResourceExhausted`. The limits stay at 16 MiB for HTTP and 4 MB for gRPC; 64 MiB is only RECOMMENDED. |
| OTLP-3 | The vendored definitions | From v1.8.0 to v1.11.1, the eight files QYL vendors change only in comments and in two Alpha profiles-only fields, `AnyValue.string_value_strindex` and `KeyValue.key_strindex` (since v1.10.0), which receivers of other signals treat as absent. Today they are unknown fields and are ignored. | **Adopt now** in QYL, in the OTLP-1 PR: re-vendor at v1.11.1 (commit `b3f7558`) and update `Protos/upstream.lock.json`, which the `VerifyOtlpProtoSourcesPinned` target checks (`eng/build/BuildVerify.cs:1483`). |
| OTLP-4 | Also since v1.8.0: restrictions on attribute values dropped ([#707](https://github.com/open-telemetry/opentelemetry-proto/pull/707), 1.9.0), `SEVERITY_NUMBER_UNSPECIFIED` allowed ([#736](https://github.com/open-telemetry/opentelemetry-proto/pull/736), 1.10.0), Retry-After may be an HTTP-date ([#806](https://github.com/open-telemetry/opentelemetry-proto/pull/806), 1.11.0), and JSON 64-bit integers and timestamps are decimal strings, with numbers also accepted on decode ([#855](https://github.com/open-telemetry/opentelemetry-proto/pull/855), 1.11.1) | The Collector converts arrays and maps for every signal (`services/qyl.collector.ingestion/OtlpConverter.cs:318-319`), passes severity 0 through (`OtlpConverter.cs:446`), and parses JSON with Google.Protobuf's `JsonParser`, which accepts both integer forms (`OtlpPayloadParser.cs:74`). Retry-After is read by clients. | **Not applicable** |

## Status, 2026-10-11 18:00 Europe/Vienna

Done:
- OTLP-1, OTLP-2 (HTTP 413) and OTLP-3 in qyl #672 (`0ad16bba`), for qyl 10.0.0.
- OTLP-2's gRPC half (the decompressed-size bound) in qyl #670 (`7e29bfb1`), released in qyl 9.2.0.

OTLP-1 per path:
- OTLP/HTTP protobuf: a strict parse first; on failure the `string` fields are rewritten on the wire with U+FFFD, guided by the message descriptor, and parsed again.
- OTLP/gRPC: the three export services bind `Export` through `OtlpExportMethodProvider`, whose request marshaller uses the same parse.
- OTLP/JSON: invalid bytes and unpaired surrogate escapes decode as U+FFFD.
