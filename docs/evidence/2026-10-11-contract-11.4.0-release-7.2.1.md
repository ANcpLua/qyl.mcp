# Toolchain, contract 11.4.0 and releases 7.2.0/7.2.1, 2026-10-11

Dated 2026-10-11, times in UTC. This record covers the toolchain pin, the
contract lockstep from 11.3.0 to 11.4.0, the npm releases 7.2.0 and 7.2.1, and
the production deploy order the 11.4.0 lockstep exposed. CI and registry results
below are not owner client observations; those stay in the
[owner-action index](../../MCP-V2-INTEROP-TODO.md#owner-only-observations-still-pending).

## Toolchain

[PR #126](https://github.com/ANcpLua/qyl.mcp/pull/126), merged as `adbd2c2`,
pins Node 24 in `mise.toml` next to Bun, deletes `.nvmrc` and removes
`actions/setup-node` from `ci.yml` and `publish.yml`. `jdx/mise-action` now
installs Node, and in `verify` it runs before `verify-contract-pins.mjs`, so the
pin check uses the pinned Node too. Renovate [PR #127](https://github.com/ANcpLua/qyl.mcp/pull/127)
moved the Bun constraint to 1.4.3. On `main` after
[PR #132](https://github.com/ANcpLua/qyl.mcp/pull/132), `mise.toml` lists:

```toml
"bun" = "1.4.3"
"node" = "24"
```

Trusted publishing needs npm 11.5.1 or newer. Node's release index shows that
every Node 24 release since 24.5.0 bundles at least that:

```sh
curl -s https://nodejs.org/dist/index.json | python3 -c "<filter v24.* releases by bundled npm>"
```

```text
node 24 latest: v24.21.0 bundled npm 11.19.0
first 24.x with npm>=11.5.1: v24.5.0/11.5.1
```

This branch therefore drops the `npm install -g npm@latest` step from
`publish.yml`.

## Production deploy order

The hosted server refuses to start on a revision mismatch
([`server/src/contract-handshake.ts`](../../server/src/contract-handshake.ts)).
Because the qyl-mcp Railway service mounts a volume, Railway stops the old
container before the new one starts. The 11.4.0 lockstep showed what that
means. Railway deployment records and deploy logs:

| Time | Service | Event |
| --- | --- | --- |
| 03:19:15 | qyl-collector | deployment `ec187c18` for `6a0cde7` (#653) created; superseded at 03:29:17 |
| 03:23:39 | qyl-mcp | deployment `79b6a48b` for `89be0fd` (#131) created |
| 03:26:58 | qyl-collector | deployment `15e4efe7` for `58bf8b2` (contains #653) created |
| 03:27:06 | qyl-mcp | previous deployment `9f8addab`: `Stopping Container` |
| 03:27:07 | qyl-mcp | `contract-revision handshake failed: collector contract revision sha256:382526f13652d18b does not match this server's sha256:3605ae27d2edf632: deploy the collector and qyl.mcp from the same contract revision`, repeated until the deployment `FAILED` at 03:27:39 |
| 03:33:05 | qyl-collector | `15e4efe7` reaches `SUCCESS` |
| 03:46:44 | qyl-mcp | redeploy `01350460` of the `89be0fd` build |
| 03:47:19 | qyl-mcp | `curl https://mcp.qyl.at/healthz` returns `{"status":"ok"}` after `502` at 03:47:03 |
| 04:03:26 | qyl-mcp | deployment `2c916c88` for `f495bf3` (#132, 7.2.1) reaches `SUCCESS` |
| 04:40:47 | qyl-mcp | deployment `ffe24407` for `0f9fe4b` (#133, 7.2.2) reaches `SUCCESS` |

The hosted server only binds after a completed handshake, so a 200 from
`/healthz` means server and Collector agree on `sha256:3605ae27d2edf632`.

**Rule for revision-changing bumps:** merge the Collector side, wait until its
Railway deployment is `SUCCESS`, then merge the consumer. A version-only bump
such as 11.3.0 → 11.3.1 keeps the revision and has no order constraint.
